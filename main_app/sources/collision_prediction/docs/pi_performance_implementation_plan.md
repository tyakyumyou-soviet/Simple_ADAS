# Raspberry Pi 向け car_program2 高速化計画

作成日: 2026-10-30
状態: 方針合意を受けた実装・検証計画。目標値と技術選択は実測で調整する。

## 1. 目的と前提

Raspberry Pi 5 と AI HAT+ 26 TOPS（Hailo-8）を使い、カメラ映像の滑らかさと、車両・歩行者等の検出結果の新しさを両立させる。動画でも動作を検証する。表示が速くても、解析結果が古い場合は達成としない。

- 現在の Raspberry Pi OS、ユーザーデータ、既存の動作環境を維持する。OSの再インストールや全面更新は前提にしない。
- 現在の HailoRT は前回確認時 4.20.0。実装時に実機のOS、カーネル、ライブラリ、HEF、Python環境のバージョンを再確認する。
- 既存のカスタム2・3・4と現在のコードを比較・復旧できるようにする。既存のユーザー変更は上書きしない。
- 物体検出はHailo-8のYOLO26nを開始点とし、n/s/mの切替を維持する。必要な処理は各段階で再測定して選ぶ。
- 今回追加したAI車線（UFLD）とAI奥行き（SCDepth）は両方停止する。従来のCPU車線、既存の距離・リスク処理は初期段階では維持する。AI車線・AI奥行きの再導入は別途の精度・速度検証を伴う将来の選択肢とする。

## 2. 現状と実測

2026-10-29に、同じ動画を処理幅320、YOLO26nで比較。ウォームアップ後120フレームのPipeline処理時間：

| 条件 | 平均 | 95パーセンタイル | 33.3 msを超えた数 |
|---|---:|---:|---:|
| カスタム4 | 17.33 ms | 79.92 ms | 10/120 |
| AI車線のみ停止 | 10.90 ms | 27.09 ms | 0/120 |
| AI奥行きのみ停止 | 14.89 ms | 79.34 ms | 10/120 |
| AI車線とAI奥行き停止 | 8.32 ms | 20.39 ms | 0/120 |

映像の読み出し、Qt UI、Pi Connect通信は計測外。短時間の一例で、認識精度や長時間性能の保証ではない。車線AI呼び出し全体は約75 msであり、現在は同じ処理ループが同期的に待つ。CPU車線を維持した上でAI車線・奥行きの表示処理を追加している。

詳細: [既存の性能分析](../outputs/logs/performance_analysis_20261029.md)。

## 3. 目標と計測値

以下は実装後の仮目標であり、達成済みの値ではない。映像・場所・認識対象を踏まえて変更できる。

- 入力30 FPSのカメラに対し、表示25〜30 FPSを目標にする。表示頻度と、最も長い表示間隔（p95/p99）を測る。
- YOLOの更新5〜10 Hz、従来車線5〜10 Hzを初期評価範囲とする。フレーム落ち時も実際の更新頻度を表示する。
- 入力時刻から解析結果反映までの年齢を中央値・p95・最大で計測する。許容値は同じ動画と実カメラによる比較結果から決める。
- カメラの取得要求値と取得実績値、処理・描画サイズ、推論回数、ドロップ数、CPU、温度、Hailo実行時間を区別して記録する。
- 誤検出、見逃し、車線の欠落、追跡のID変化、警告の反応・誤警告も変更前後で観察する。速度のみを合格条件にしない。
- 温度・負荷が安定するまで連続運転し、停止・再開・再起動の繰り返しでリソース解放を確認する。長時間の測定時間は実機条件に応じて設定する。

## 4. 機能の取捨選択とプロファイル

1. 速度改善用の新しいプロファイルを用意し、AI車線・AI奥行きは既定OFFにする。両モデルを初期化・推論・描画しないことを個別の回数と実機ログで確認する。
2. 従来のCPU車線検出、既存の警告・距離、YOLO、ユーザーのカスタム設定を維持する。個別に停止した場合の影響を明示する。
3. YOLO・従来車線・AI車線・AI奥行きは、それぞれ実時間ベースの更新周期を持つ。停止中のAIはモデルを開かず、負荷を発生させない。
4. 新プロファイルの保存方法、各機能ON/OFF・周期の表示を整え、アプリ再起動後も設定が反映されるようにする。従来の設定名が未使用の場合は、実装・表示・説明を一致させる。

## 5. 映像・解析・表示の構成

```text
カメラ取得（元画像＋取得時刻＋番号）
   ├── 最新プレビュー → 描画周期に合わせて表示
   └── 解析待機スロット（最新1枚） → 解析処理 → 時刻付きの最新結果
                                                        └── 表示・警告へ
```

- 既存のカメラ取得は別スレッドで最新画像を保持している。これを活用し、表示が解析完了を待たない構造へ変更する。
- 解析中は入力を無限に積まず、待機中の画像を最大1枚に制限し、新しい画像が来たら古い待機画像を上書きする。処理中の画像を含めると最大2枚になり得る。
- UI通知も古い画像が溜まらないように制限する。画像の所有権、上書きと読み取りの競合、停止・再開・モデル変更時の資源解放を設計する。
- 推論はアプリ本体から待機を切り離す。HailoRT 4.20の利用可能な非同期APIを確認し、対応可能なら非同期APIを使用する。使えない場合も専用ワーカーで表示から分離できる。これらの方式は明確に区別して報告する。
- Hailo-8は共有資源。VDeviceの所有者を一箇所にし、モデル間の競合、二重初期化、推論の同時実行数を制御する。停止時に推論完了・解放を待ち、再接続を検証する。
- 表示用と解析用の時刻・フレーム番号・サイズを保持する。解析結果が設定した年齢を超えたら、古い結果として表示・警告から外す。古さの閾値は実測と用途に基づき設定する。
- 車線・追跡・危険度推定の経過時間は、処理回数ではなく撮影時刻の差を使う。スキップ後の速度、TTC、追跡寿命、警告の消去条件を点検する。
- ライブ動画の遅延を抑える再生と、動画の全フレームを処理するオフライン解析は別モードとする。停止・一時停止・シーク時は古い画像と結果を破棄する。

## 6. 入力・処理・表示の解像度

- カメラの取得幅・高さ・フォーマット・希望FPSを指定し、オープン後の実際の取得値を取得・表示する。
- 前回のカメラ実機情報は320×240、352×288、640×480、1280×720。対応FPSはフォーマットにより異なる。320×240 YUYV / MJPEGは30 FPS対応。起動後に現在の接続カメラで再確認する。
- 540幅は前回一覧にはない。取得解像度として希望された場合は、カメラが受け付けた実際の値を表示し、対応しない場合は通知する。カメラに540を要求したのに540で取得できていると誤表示しない。
- アプリ内の処理幅は540など任意に指定可能とする。取得→処理→描画の各サイズを明示し、縦横比と座標の対応を維持する。取得より大きくする拡大は元の精細さを増やさないことを説明する。
- YUYV/MJPEGを実機で比較し、CPU負荷・遅延・画質とサポート状況から選択する。指定変更時の再オープンと失敗時の復帰を扱う。
- HailoのHEF入力サイズは別で固定される。取得サイズ・処理サイズの変更がHEF自体の推論時間に与える影響を実測する。

## 7. 描画・画面更新・CPU最適化

- 描画周期を実際のレンダリング前に判定し、描画しないフレームでは描画・Qt画像変換・通知を実行しない。AI更新周期と独立して設定する。
- 通知の滞留を避け、画面には最新フレームを優先する。映像・枠・警告が別時刻であることを時刻管理で扱う。
- 再利用できる縮小画像、グレースケール、描画結果、警告表を共有・キャッシュし、重複変換とコピーを計測して削る。
- モデルロードは初期化のタイミングを見直し、初回の停止と準備時間を分けて表示・計測する。
- 自車動作推定や追跡の軽量化は、前後の結果を確認してから選ぶ。機能停止だけを高速化の成果としない。

## 8. Python / Rust / C++ / GStreamer の検討

最初に、現行Python + PySide6 + HailoRTで処理の分離と適切なデータ受け渡しを実装し、実測の比較基準を作る。その上で、計測上の支配的な部分だけ別の選択肢で小規模に試作する。言語の書き換え自体を成果としない。

| 候補 | 利点・候補箇所 | 検証事項 |
|---|---|---|
| Python + 既存のOpenCV / HailoRT | 既存UI・追跡・設定を活用し段階導入できる。OpenCV・HailoRTの内部は既にネイティブ実装 | UIやPython側の後処理・コピー・待機がどこまで残るか |
| Rust | 入出力・並行処理・画像後処理の限定的な実装候補。GStreamer公式Rustバインディングがある | ARM64でのビルド、既存HailoRT 4.20とのABI、バッファ所有権、Python/Qtとの橋渡し・コピー量 |
| C/C++ | HailoRTの公式C/C++ APIを直接使える。CPU側の重い箇所や推論ワーカーの候補 | SDK/ヘッダー・ライブラリと現行4.20の整合性、保守性、例外・停止処理 |
| GStreamer | カメラ取得、動画デコード、バッファ管理やHailoプラグインの候補。Python / Rust / C/C++から扱える | 現行OS・HailoRTとのプラグイン互換性、USBカメラ、YOLO26の出力処理、Qtへの受け渡し |
| 外部機材 | 現在のPi/Hailoで必要な認識速度・精度を満たせない時の候補 | 追加費用、電力、通信・転送・全体遅延 |

HailoRT公式リポジトリはC/C++、Python、GStreamerを記載し、Hailo-8にはhailo8ブランチを案内している。Rustからのアクセス候補はGStreamer Rustバインディング、またはHailoRT C APIへのFFI。第三者Rustバインディングは存在するが、現行のHailoRT 4.20および各HEFとの互換性は未確認であり、依存関係・保守状況・ライセンス・ABIを評価する。GStreamerの存在だけで現在のYOLO26出力形式をデコードできるとはみなさない。

試作する場合は、同じPi、同じ映像、同じHEF、同じ解像度・検出条件・ウォームアップで、次を比較する。

- プレビューFPS、停止間隔p95/p99、結果年齢、YOLO更新頻度、CPU使用率、メモリ、温度。
- 各境界での画像コピー数・転送量、起動・停止時間、モデル切替、エラー復帰。
- YOLO座標、クラス、信頼度、既存追跡・警告との互換性。挙動と精度が同等であること。
- インストール・クロスビルド・保守の難しさ、既存OSとHailoRTに与える影響、依存ライブラリのバージョンとライセンス。

採用基準は「目標を満たし、測定上の改善が再現し、既存OS・ユーザー設定・認識結果を維持でき、保守できること」。比較の結果、Python継続・部分Rust化・部分C++化・GStreamer化のいずれも選び得る。Rust、C++、GStreamerは現時点では未測定であり優勝候補を断定しない。

## 9. 実装順序

1. ラズパイ起動後の接続・OS・HailoRT・ソース差分・機材状況の確認。既存プロファイルと設定のバックアップ、基準測定。
2. 新プロファイルにAI車線・AI奥行きの停止を実装し、モデルのロード・推論・描画が行われないことを確認。既存のCPU車線とYOLO動作を確認。
3. カメラ・表示・解析を分離し、最新1枚の待機、結果時刻・失効、停止と再起動を実装する。
4. YOLO、従来車線、AI車線、AI奥行き、表示に独立した実時間周期・ON/OFFを用意する。動画の再生モードと全フレーム解析を扱う。
5. カメラ取得サイズ指定と実取得結果の表示、処理・表示解像度の独立設定を追加。320×240と640×480を比較する。
6. 描画の実際の間引き・UI通知制限・画像コピーや後処理を改善し、機能ごとに速度・精度を再測定する。
7. 目標に届かない要因を測定し、Python、Rust、C++、GStreamerのうち必要な候補だけを同条件で試作。必要なら機材分担も比較する。
8. 同一動画、実カメラ、長時間、モデル切替、入力変更、停止・復帰で検証し、最終採用案と測定結果を記録する。既存の作業環境を保持した状態でPiに反映する。

## 10. 検証と完了条件

- 単体: 最新1枚置換、異常終了、古い結果の失効、入力時刻と座標変換、各周期・ON/OFF、シーク・停止・再起動、入力解像度の交渉失敗を検証する。
- 同一動画: 旧版と新版で同じ時間区間・HEF・入力条件を用い、フレーム別の検出内容、車線、追跡・警告と時間を比較する。
- 実カメラ: 要求値と実取得サイズを確認し、320×240・640×480で表示、推論頻度、結果年齢、連続動作を記録する。540幅がサポート外なら明示する。
- 実機負荷: Pi Connectと可能ならローカル表示を分けて確認し、表示FPS・取得FPS・推論頻度・Hailo使用・CPU・温度・フレーム落ちを測る。起動直後と定常状態を分離する。
- 機能: AI車線・AI奥行きの推論数がゼロ、YOLOはHailoで推論、CPU車線・警告の継続、n/s/m切替、保存・再起動を確認する。
- 設定値と表示値が実際の動作と一致し、全フレーム解析とリアルタイム再生の挙動が説明できる。
- 効果は改善前後の測定値で報告し、未達の目標、認識への影響、残る制約を明記する。
