## 計測・確認結果

- 同じ動画の最初の144フレームから先頭24を除く120フレーム、処理幅320、YOLO26n。新設定は描画込みのPipeline処理時間が平均7.75 ms、p95 19.73 ms、33.3 ms超0/120。以前のカスタム4は平均17.33 ms、p95 79.92 ms、10/120。検出・車線周期の制御も変更されているため、完全な同条件比較ではない。どちらも動画デコード・Qt UI・画面転送は除外。
- カメラで取得だけを計測: ドライバーバッファ1枚で約7.9 FPS、4枚で約15.2 FPS。4秒ずつ、320×240 YUYV、実験時の条件での一例。4枚にすると取得前のバッファ滞留の可能性があり、カメラ露光からの真の遅延は未測定。
- 動画の実時間優先では、元動画（3144×1764、HEVC）でoffscreen表示約7 FPS。同じ動画から作った一時的な640×360 H.264・6秒の検証映像では表示約29.7 FPS、YOLO約4.6回/秒。精度と長時間性能は未検証。
- 取得形式YUYV/MJPEGを比較した例ではそれぞれ約15.25／15.14 FPS。入力は30 FPSと報告されたが、実測は異なった。露出を一時変更しても1枚バッファでは約8.5 FPSだった。元の設定に復旧済み。実際の入力FPSを画面に表示する。
- 4枚設定の検証用画面で、入力約16.7 FPS、表示約14.7 FPS、YOLO約4.2回／秒、車線約4.2回／秒、結果の経過約60 msを表示。画面表示はoffscreenであり、Pi Connect転送込みの測定ではない。結果の経過はOpenCVがフレームを読み取った後からの時間で、センサー露光時刻からの実遅延ではない。
- カメラに320×240・640×480を要求すると同サイズで取得。540×405要求では640×480を取得。表示側で差分を通知する。
- 実機でYOLO26 n/s/mを切替し各Hailo推論を確認。AI車線をOFF→ON→OFFしYOLOに戻ることを確認。
- 遅い模擬推論を使い、プレビューが継続し待機画像が置き換えられることを確認。動画全フレーム／実時間優先と描画の間引き、既存プロファイル切替、YOLO26デコードのテストが通過。

## 未完了・制約

- HailoRT 4.20の `run_async` を使い、YOLO26nの動画フレーム1枚を同期APIと比較したところ、6つの出力テンソルは一致した。単一フレームの試作であり性能評価ではない。新経路はPythonの専用ワーカー内で既存の同期推論APIを呼び、ネイティブ非同期APIの組み込み・連続運転検証は未実施。
- カメラと動画の実時間優先ではプレビューと解析を分離し、遅れた動画フレームをスキップする。全フレーム処理モードは従来の直列ループを使用する。
- 検出結果の期限切れ表示は実装済みだが、従来の追跡・光学フロー・速度推定にはフレーム数／平均FPSを前提とする箇所が残り、全てが撮影時刻差に対応したわけではない。警告・速度・TTCの精度に関して追加実装と検証が必要。
- 自車動作推定とBB追跡のグレースケール共有など、より踏み込んだCPU最適化は未実施。
- カメラの約15 FPSの原因は確定していない。露出、USB、ドライバー等の影響は別途調査し、実際の走行条件でも測る必要がある。
- 十分な時間の連続負荷、温度、Pi Connectと現地表示の比較、注釈付き映像を使う検出・車線・警告の精度比較は未実施。実走行での安全性は確認していない。
- 実機にGStreamer `hailonet` があり、HailoRTには `create_infer_model` が存在。Rust/cargoはPATH上で見つからなかった。Python・Rust・C++・GStreamerの同条件の試作比較は未実施。追加の導入は現行OSやHailoRTへの影響を確認してから行う。
