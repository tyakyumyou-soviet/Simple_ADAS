# 暗所FPS追加検証 2026-10-31

## 結論

暗所で新しい画像を30 FPS取得する問題は未解決。既定バッファ数に別の速度低下要因を確認し修正したが、現在のPi高速プロファイルは元から4枚のため、この変更によって暗所30 FPSになるわけではない。

ユーザーには撮影対象が少し見える暗所での準備を依頼したが、この記録の計測終了時点では準備完了の返答を受けていない。計測画像の平均値は低く概ね安定しているものの、撮影対象や照明が完全に同じ条件であったとは保証できない。

## 環境と計測条件

- Piの実際のカーネルを再確認: 6.12.109+rpt-rpi-2712。以前の問い合わせ文案にある6.12.25は過去のSSHログ由来であり、今回の環境の値に修正した。
- CMS-V43BK、1bcf:2281、UVC 1.00、bcdDevice 0.14。
- 320×240、30 FPS指定。各条件約2秒安定待ち＋約4秒取得。短時間比較であり、長時間・実車検証ではない。
- 温度確認時43.3℃、throttled=0x0。

## 実施した追加施策

1. 自動露出→手動露出へ切替を繰り返し、絶対露出1250/3/30/333/100（100µs単位）を再送。再オープン前後の設定、最短露出、ホワイトバランス固定も比較。バッファ1枚の条件では概ね8.5 FPSのまま。バッファ自体の影響を後述の比較で分離した。
2. 25/20 FPS指定、352×288、MJPEG 320×240・640×480も比較。バッファ1枚では約5.8〜8.5 FPS。ここからカメラ内部FPSを直接推定しない。
3. FFmpegでOpenCV・画像変換・Qt・AIを外し、YUYV 320×240を取得。約17 FPS。指定30 FPSというメタデータと実際の受信数は区別した。passthroughで出力し、フレーム複製は使っていない。
4. 同じOpenCV経路でバッファ数を比較。1枚→4枚→8枚→4枚で速度差が再現した。
5. バッファ4枚で最短露出、78、156、周波数補正無効を比較。それでも30 FPSに改善しなかった。
6. usbmonでカメラの制御転送のみを記録。V4L2の手動モード切替はCT unit1/selector2へ01、露出4/3/166はselector4へ04000000/03000000/a6000000として送信され、完了ステータス0だった。自動露出復帰は08。設定がUSBドライバーから送られることは確認できたが、センサー積分時間がその通り変わったことを保証しない。調査後usbmonモジュールを解除。
7. 標準のusbresetコマンドで対象カメラのみリセット。成功。リセット直後の露出/周波数は3/0となっており、その状態で約15.0 FPS。リセットだけでは30 FPSに復帰しなかった。その後166/1および自動露出3へ明示的に戻し、読み戻しで確認。

## 追加調査

LinuxのUVC公式資料は可変FPS許可を露出優先制御で設定する仕様を説明しているが、このカメラではその標準制御が広告されず、前回USB読み出しにも応答していない。

fwupdのSunplusカメラ実装も調査したが、対応対象は1bcf:2cedで、この個体1bcf:2281ではない。これはファームウェア更新経路の資料であり、暗所FPS修正やCMS-V43BKへの互換性を示すものではない。導入・更新していない。未確認のXU項目を書き換える根拠には使わない。

USB直接書込の別案は自動承認レビューがリスクと復元方法の不足を理由に拒否し、実行していない。その経路を迂回して実行せず、通常のV4L2操作とUSB制御転送の観測で設定送信を検証した。

## 次の切り分け

同じUSBカメラをMacにつなぎ替えて、AVFoundation経由で同じ暗い対象を取得する比較を提案した。別カメラ・追加照明は不要だが、USBのつなぎ替えはユーザーの操作が必要。

- Macで暗所30 FPSを出せれば、Linuxの設定送信・取得開始手順・ドライバーとの違いを追う根拠になる。
- Macでも同様に低下すれば、カメラ内部の共通動作という仮説を強めるが、設定差もあるためハードウェア限界と断定しない。
- MacにはFFmpegが存在する。まだMacのカメラ撮影は開始していない。
