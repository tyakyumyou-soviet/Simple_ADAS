# ver28以降の奥行き・障害物判定の改善計画

調査日: 2026-11-01。以下は提案であり、未実装・未検証の方式を含む。

## 改訂方針: 速度最優先で判断処理を改善する

ユーザーの追加要件により、次回修正ではモデル追加・変更を主軸にせず、現在のモデル出力の解釈と判断処理を優先する。追加AIモデル、密なオプティカルフロー、全画面の高解像度解析は導入しない。奥行き間隔0.6秒、現在のモデルと入力条件を比較基準に固定する。前述の更新周期短縮や新モデルは後続の別実験に移す。

### コード確認で分かった改善候補

以下はコード上の構造から想定される弱点であり、全てが観測済みの誤検出の原因と確定したわけではない。

| 現行処理 | 想定される問題 | 次回の比較案 |
| --- | --- | --- |
| フレームごとの5/95パーセンタイルで近さを正規化 | 背景構成の変化で対象の近さも変わる | 現フレームの近さと、対応する対象の時間変化を区別する。未校正の相対値だけで強い警告を出さない |
| 行全体の深度分布から路面傾向を一次近似 | 大きな壁や車が路面推定を汚す可能性 | 除外領域・既知対象を避け、信頼できる路面候補だけで頑健に推定する。十分な路面がなければ不明とする |
| 連結成分の外接矩形全体から深度・進路重複を求める | 矩形内の路面や空白が判定に混入する | 縮小画像上の実際の候補マスクを集計に使い、描画枠と判定領域を分ける |
| 未分類候補は矩形IoUで対応付け、消失時に即削除 | 分裂・結合で履歴が途切れる可能性 | 位置・面積・深度の整合性を含む小規模な対応付けを比較する。短期の履歴保留と警告継続は分け、古い警告を残さない |
| 特徴点が不足するとtrack_valid=Falseで対象を処理しない | 無地の壁で接近根拠を失う | 追跡不能を障害物なしと混同しない。深度更新時に再評価し、必要な領域だけで輪郭・ブロック照合を試す。追跡失敗を高危険度の根拠にはしない |
| 固定加重スコアと複数の閾値・観測数で警告 | どの根拠で警告したか分かりにくく、解除や確認遅延の調整が難しい | 存在・進路重複・接近・観測品質を分け、候補→確認→接近注意の明示的な状態遷移と解除条件を比較する |

### 次回修正の範囲と順番

1. **現状の計測と説明可能性**: 評価用の短区間、候補棄却理由、処理区間別の時間を整える。ログは評価時のみ有効にし、通常動作で毎フレームのファイル書き込みを増やさない。
2. **候補領域の扱い**: 車体除外マスクを事前生成し、縮小深度画像の候補マスクを集計に使用する。下部一律除外は既定の互換動作として残し、カメラ別マスクを選べるようにする。既知対象の重複除外に未確認トラックまで使う現行条件も比較する。
3. **路面推定と対象履歴**: 信頼できる画素だけで路面傾向を推定し、候補の分裂・結合や一時欠落で履歴が不必要に途切れないようにする。場面切替・大きな画面変化では履歴を解除する。
4. **判断方式の比較**: 既存スコア方式と、根拠別の状態遷移方式を同じ候補列でオフライン比較する。本番で両方式を常時実行せず、採用した方式だけ動かす。警告を遅らせるだけの平滑化を避ける。
5. **残った壁の見逃しに限定した追加処理**: 必要な領域・更新時刻だけで安価な輪郭/ブロック照合を検討する。元映像に情報がなければ判定困難とし、無理に接近と判断しない。

### 処理予算と採否

- 重い候補集計・対応付け・路面推定は原則として奥行き更新時のみ行う。画面更新ごとの処理は既存追跡、期限切れ処理、描画に必要な軽い更新に限定する。
- 解析幅160px・候補上限12を基準とし、候補がなければ追加追跡を行わない。マスク・縮小画像・集計値は可能な範囲で再利用し、全解像度コピーを増やさない。
- 仮の許容予算は同一条件の繰り返し計測で表示FPS低下3%以内、撮影から表示までの遅延95パーセンタイル増加5ms以内とする。これは達成済みの数値ではない。計測ばらつきを先に確認し、測定不能なら主張せず測定方法を整える。
- カメラ入力FPSが上限になって差が隠れる場合は、解析処理時間とワーカーの余裕、最新画像の経過時間も比較する。速度の余裕を失う案は採用を見送り、縮小・間引き・削除を検討する。
- 検出品質は誤警告だけでなく、確認できる障害物の見逃しと警告開始時刻も比較する。速度維持を優先しつつ、警告を全て消すことで成績を良くしない。

下記の研究・モデル調査は中長期の候補集であり、この次回修正に一括導入するものではない。Rust/C++移植も計測で必要性が分かった箇所だけに限定する。

## 現在地

ver28は障害物の方向表示、検出範囲の枠表示、回転時の過大警告の抑制、ボンネット対策を固定した比較基準とする。現在の奥行きは相対値であり、距離・衝突までの秒数として校正されていない。既定の奥行き更新間隔は0.6秒。既存の検証結果と制約は[ai_depth_risk.md](ai_depth_risk.md)参照。

画面下20%の除外は暫定策であり、そこにしか映らない低い障害物も消す。特徴点の乏しい壁は追跡・接近確認に失敗し得る。これらを単なる閾値緩和で直すと誤警告が増えるため、原因別に対処する。

## 1. 再現できる評価を先に整える

- 手元のMy Movie 3を場面・カメラごとに分割し、路面誤検出、側壁の平行通過、旋回、暗所、物体接近の短区間を固定する。映像は外部へ送信しない。
- 障害物の領域・方向・警告してよい時間を人が確認し、判断できない箇所は不明とする。同じ場面の近接フレームを調整用と評価用に分けない。
- 候補が消えた理由を、深度不足、除外領域、追跡失敗、接近根拠不足などに分けて記録する。警告数が減っただけで改善としない。
- 誤警告/分、評価対象イベントの検出率、警告開始時刻、表示遅延の中央値・95パーセンタイル、入力/表示FPSを比較する。動画にない壁への接近性能は未評価とする。

## 2. 路面・車体・立面を区別する

固定の下部除外を、設置カメラごとのボンネット/ダッシュボード除外ポリゴンへ置き換える。My Movieのような異なるカメラの編集動画では場面ごとの設定を使う。

次に、カメラ内部パラメータ・高さ・傾きを校正し、信頼できる路面領域から路面の形状と立面との差を評価する。現在は路面モデル未配置時の固定台形マスクもあるため、本物の路面推定が動いているかを先に確認する。相対深度からそのまま正確な3D座標を作らず、幾何の整合性・実測との誤差を検証する。

着想は地面の事前知識を利用する[MonoGround（CVPR 2022）](https://openaccess.thecvf.com/content/CVPR2022/html/Qin_MonoGround_Detecting_Monocular_3D_Objects_From_the_Ground_CVPR_2022_paper.html)。論文のモデルをそのまま導入する計画ではない。

## 3. 時間方向の情報を強化する

- 特徴点追跡に加え、領域のブロック照合・線分・輪郭の変化を比較し、無地の壁で使える根拠を探す。旋回による画面変化と接近を分離する。
- 単一フレームで警告を切り替えず、観測の継続と品質に応じた状態遷移・解除条件を設ける。「根拠なし」と「障害物なし」を区別する。
- 0.6秒間隔で3観測を要求すると初回から1.2秒かかる。疑わしい領域が出た時だけ奥行き更新を速める方式を検証し、YOLOと表示の遅延が増えないよう計測する。

時間的一貫性の比較候補は[Video Depth Anything（CVPR 2025、公式実装）](https://github.com/DepthAnything/Video-Depth-Anything)。まずMac上のオフライン比較に限定する。別モデルの出力は正解データではなく、Hailo-8での動作やPi上の速度も確認されていない。

## 4. 奥行きモデルの適性を見直す

Hailoの[公式SCDepthV3設定](https://raw.githubusercontent.com/hailo-ai/hailo_model_zoo/master/hailo_model_zoo/cfg/networks/scdepthv3.yaml)はNYU Depth V2を基底にし、屋内の学習済みモデルを参照する。現在のHEFも同じ重みかは出所の確認が必要であり、道路での不調の原因と断定しない。

新候補はYOLO26n-depth。既存のYOLO26物体検出モデルとは別物である。[Ultralytics公式Hailo文書](https://docs.ultralytics.com/integrations/hailo)には深度モデルの変換経路があるが、検証機はHailo-8Lであり、手元のHailo-8は実機確認が必要。入力・出力の復元処理、コンパイラとHailoRTの組合せ、道路・夜間に合う量子化校正画像を確認する。

最初に同じ評価場面で元モデル同士を比較し、その後にHailo-8用HEFの入手または変換の可否を調べる。公式コンパイラはLinux x86_64用なので、Apple Silicon MacとPiだけで大きな変換環境を再構築する前に、容量・所要時間・代替環境を見積もる。モデル変更が有利でなければ現行を維持する。

## 5. 夜間と処理効率を別々に評価する

夜間は入力FPSと検出の品質を分けて測る。画像補正で存在しない情報が復元するとは扱わない。深度と意味領域を併用する研究例として[DepthSegNet24（ACCV 2024）](https://openaccess.thecvf.com/content/ACCV2024/html/Thanh_DepthSegNet24_A_Label-Free_Model_for_Robust_Day-Night_Depth_and_Semantics_ACCV_2024_paper.html)を参考に、路面・壁・車の区別を検討する。Hailo-8向けモデルの入手・変換は未確認。

速度は[Hailo公式C++奥行き実装](https://github.com/hailo-ai/hailo-apps/blob/main/hailo_apps/cpp/depth_estimation_mono/README.md)を参考に、共有デバイス上の非同期実行、前処理、コピー量を計測する。Rust/C++への移植は計測で支配的と分かった箇所に絞る。言語変更だけでモデルの誤認識は改善しない。

## 中長期の候補（次回修正後に再評価）

1. 評価区間・正解/不明ラベル・候補棄却理由の記録を整備する。
2. カメラごとの除外領域と路面/立面判定を改善する。
3. 壁の追跡と継続確認、必要時の更新周期短縮を比較する。
4. YOLO26n-depth等の候補を同一条件で比較し、Hailo-8用成果物が確保できたものだけ実機評価する。
5. 改善ごとに精度・警告遅延・表示速度を比較して採否を決める。現在の動画で分からない性能は結論を保留する。
