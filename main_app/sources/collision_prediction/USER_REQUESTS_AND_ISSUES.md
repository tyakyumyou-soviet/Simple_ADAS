# ユーザー指摘・要求まとめ

このファイルは、これまでユーザーが指摘した問題、追加要求、品質基準を後から確認できるように整理したものです。実装時は `PLAN.md`、進捗記録は `PROGRESS.md`、要求確認は本ファイルを参照します。

## 基本方針

- macOS での利用を前提にする。
- 個人利用なので、ライセンス問題よりも動作・品質・完成度を優先する。
- 必要な情報・モデル・ライブラリはインターネットから参照/ダウンロードしてよい。
- 必要に応じてコマンド実行、テスト、評価動画生成を行ってよい。
- `.md` ファイルに書かれたルールや計画を参照して進める。
- 途中で止めず、できるだけ完成状態まで持っていく。
- 警告や検出表示は、削除せず残す。

## 環境・起動・設定に関する要求

- 現在の作業ディレクトリを確認できるようにする。
- `config/realtime_cpu.yaml` のような設定ファイル指定が必要か説明する。
- MPS とは何か、`--config config/realtime_cpu.yaml` を付けると何が変わるか説明する。
- macOS でしか扱わないため、`config/realtime_cpu.yaml` を標準で読み込むようにする。
- 設定はUIから選択できるようにする、という初期要求があった。
- その後、品質選択が複数あると分かりにくいため、品質/実行プロファイルは1つにまとめる要求へ変更された。
- Anaconda仮想環境で `pip install -r requirements.txt` を実行したときの依存競合について説明する。
- 必要ライブラリをインストールする `pip` コマンドを生成する。
- 入力に使える映像ファイル形式を説明する。

## 入力・UIに関する要求

- 動画ファイルとカメラ入力を扱えるようにする。
- 高解像度入力、例: `2778x1284` の映像でも自動縮小して軽く動作するようにする。
- UI上に検出結果が必ず見えるようにする。
- 車両を検出したら、画面上に枠とラベルを表示する。
- `car` など、認識したクラス名を表示する。
- 車両の進行方向をベクトルで表示する。
- 車両をトラッキングし、進行方向・履歴から衝突予測へ使う。
- 信号や標識の検出は重要度が低いため削除または標準処理から外す。
- 視認性補正も削除または標準処理から外す。
- 品質選択UIは1つにまとめ、ユーザーが迷わないようにする。

## 性能・軽量化に関する問題指摘

- 動作が遅すぎる。
- ほとんど動かない。
- 入力画像が高解像度だから遅いのではないか、という疑問があった。
- 自動で画質を落として処理するべき。
- 精度を多少犠牲にしてでも、もっと軽量に動かしたい。
- もっとスムーズに動いてほしい。
- 動画やカメラ入力のFPSに応じて、何フレームごとに処理するか決めたい。
- 30fpsなら当初6フレームに1回程度がよいという話があった。
- その後、30fpsなら3フレームに1回処理するよう要求が変更された。
- 再生フレームレートはあまり落としたくない。
- 処理が一定以上遅れるなら、認識できないフレームはスキップして再生の滑らかさを優先する。
- ただし、処理頻度を下げすぎると検出頻度が激減して意味が薄くなるため、単純な大幅間引きは避ける。
- 普段速いのに突然遅くなる、または遅いのに突然速くなる原因を分析する。
- 検出が発生した瞬間に重くなるのではないか、という疑問があった。
- 他にも軽量動作の工夫を思いつけば実装する。
- 根本原因候補として、MPSが使えずCPU推論になっている点を調査する。

## 車線・台形ゾーン・画角補正に関する要求

- 車線は点線もあるため、点線車線も考慮する。
- 中心の基準線ではなく、中心付近の赤い台形ゾーンを調整対象にする。
- 台形ゾーンは、カメラ設置位置や画角に応じて修正できるようにする。
- 台形ゾーンを左右に動かせるようにする。
- 台形ゾーンを前後に伸ばす/縮めるようにする。
- 台形ゾーンの左右の曲がり/寄せは、カーブや対向車との関係に影響するため調整可能にする。
- デフォルトでは適宜自動修正する。
- 手動でも設定できるUIを作る。
- 明らかに画角が変わった映像では、基準となる台形ゾーンを修正する。
- 台形ゾーンの自動修正が実装されていない、と指摘があった。

## 検出・表示に関する問題指摘

- 以前は車を検出したら画面に表示されていたのに、その後表示されなくなった。
- 全然検出できていない。
- 画面に表示されない。
- ちゃんと分析しているのか、という強い指摘があった。
- 「なんでもいいから、とにかく表示されるように修正して」と要求された。
- フォールバックでもよいので、検出枠・ラベル・台形ゾーン・警告が見える必要がある。
- `candidate` のような曖昧な表示より、車両候補は `car` として見える方がユーザー要求に近い。
- 車両ラベルが他のラベルに隠れないようにする。
- 警告オーバーレイの日本語が `????` にならないようにする。

## YOLO・物体検出に関する要求

- 必要に応じてYOLOを使う。
- YOLOで車両や歩行者を検出する。
- 検出した物体を `car` などのラベルで表示する。
- ByteTrackなどでトラッキングし、IDを付与する。
- 車両の進行方向をベクトルとして画面に描く。
- 検出結果を衝突予測に使う。
- 信号や標識検出は後回しまたは不要。

## 衝突検知・危険判定に関する要求

- 対人対物衝突検知を行う。
- 歩行者を検知する。
- 車を検知する。
- 交差点で、対向車と自車がぶつからないか判断する。
- 衝突を予測・判断する。
- 対向車が右左折してこちらにぶつかるかどうかは、その車を必要なフレームごとにトラッキングし、進行方向から判断する。
- 普段の対向車、つまり直進しているだけの対向車は衝突とは判断しない。
- 歩道上の歩行者は検知対象から外す。
- 飛び出してきた歩行者もどうにか検知したい。
- 前の車が発進したら検出する。
- 前の車との車間距離が近すぎたら通知する。
- これらの要件が満たせていない、という指摘があった。

## 削除・優先度低下が明示された機能

- 信号検出はどうでもいいため削除または標準処理から外す。
- 標識検出はどうでもいいため削除または標準処理から外す。
- 視認性補正は削除または標準処理から外す。
- 軽量化のために削除した警告や重要表示は残す。

## 現時点で特に重要な満足条件

- アプリを起動したら、標準設定1本で動く。
- 車両検出が画面に見える。
- `car` ラベル、ID、距離、進行方向ベクトルが見える。
- 歩行者も検出枠が見える。
- 台形ゾーンが見える。
- 台形ゾーンをUIで調整できる。
- 車線・台形ゾーン・検出枠・警告が、処理スキップ中でも消えにくい。
- 30fps入力では概ね3フレームに1回程度の解析を行う。
- 処理が遅い場合は再生の滑らかさを優先し、解析を適宜スキップする。
- 警告は日本語で読める。
- 実装後は、テストだけでなく注釈付き動画やプレビュー画像で目視確認する。
