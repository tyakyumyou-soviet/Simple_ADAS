# 技術選定の意思決定記録（ADR）

Architecture Decision Records — なぜこの技術を選んだかの記録。  
将来の開発者（人間・AI問わず）が意思決定の背景を理解できるように残す。

## ADR-001: バックエンド言語に Rust を採用

**日付**: 2026-06-19  
**ステータス**: 採用

### 背景

実行環境が Raspberry Pi 5（リソース制約あり）で、速度・軽量化を最優先とする要件があった。

### 検討した選択肢

| 言語/FW | メモリ | 起動速度 | 開発速度 | 備考 |
|---|---|---|---|---|
| Rust (Axum) | ~5MB | <100ms | 低め | 最速・最軽量 |
| Go (net/http) | ~10MB | <100ms | 高い | バランス型 |
| Python (FastAPI) | ~80MB | ~2秒 | 最高 | 重い・遅い |

### 決定

**Rust (Axum)** を採用。

- 速度・メモリ効率が最優先要件である
- 保守は AI に委ねるため、開発速度の低さは許容できる
- 親システムが Python でも Rust でも、このサーバーは独立したバイナリとして動作するため言語統一は不要

### トレードオフ

- ビルド時間が長い（リリースビルドで 2〜5 分）
- Rust の学習コストが高い（AI 保守前提のため問題なし）

## ADR-002: フロントエンドに Vanilla JS を採用

**日付**: 2026-06-19  
**ステータス**: 採用

### 背景

スマートフォンでの表示速度を最優先とする。

### 決定

React/Vue/Svelte などのフレームワークを使わず、Vanilla HTML/CSS/JS のみで実装する。

### 理由

- フレームワークのランタイム（React ~40KB、Vue ~30KB）が不要
- フロントエンドの機能は一覧表示・動画再生・ダウンロードのみで、フレームワークの恩恵が小さい
- 静的ファイルをバイナリに内包（`include_str!`）する設計との親和性が高い

## ADR-003: データベースを使用しない

**日付**: 2026-06-19  
**ステータス**: 採用

### 決定

SQLite 等のデータベースを使わず、ファイルシステムを直接読んでメモリキャッシュする。

### 理由

- 動画メタデータはファイルシステムから取得できる（追加情報が不要）
- 依存関係が増えるとデプロイが複雑になる
- Raspberry Pi の SD カードへの書き込み回数を最小化したい

## ADR-004: HTTP Range Requests をサーバーサイドで実装

**日付**: 2026-06-19  
**ステータス**: 採用

### 背景

`tower-http` の `ServeFile` で Range を自動処理できるが、ダウンロードとストリーミングを同一ファイルに対して異なるヘッダーで提供するため、カスタムハンドラーで実装する。

### 決定

`tokio::fs::File` + 手動 Range ヘッダー解析で実装する。

## ADR-005: 認証をオプション扱いにする

**日付**: 2026-06-19  
**ステータス**: 採用

### 決定

LAN 内専用サービスとして認証はデフォルト無効。`config.json` の `auth` フィールドで Basic Auth を有効化可能にする。

### 理由

- 家庭内 LAN での個人・家族利用を主目的とする
- HTTPS なしの Basic Auth はセキュリティ的に弱いが、LAN 内なら許容範囲
- インターネット公開する場合はリバースプロキシ（nginx）で HTTPS + 認証を追加すべき
